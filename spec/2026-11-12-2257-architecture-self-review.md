## 背景 / 问题

`spec/13` 与 `spec/17` 完成后，架构指标全部达标（违规 0、测试 348、无超阈值文件），
但盘点依赖数时发现一个**我自己造成的问题**：

| 类型 | 注入的闭包/依赖数 |
| --- | --- |
| `LiveFrameApplier` | **19** |
| `NotificationBridge` | **17** |
| `LiveStreamRunner` | **16** |
| `SessionActions` | 12 |

`LiveFrameApplier.Providers` 有 19 个字段，意味着它需要知道模型里的 19 件事才能工作。
这跟原来 `ConnectionModel` 是上帝对象的区别，只是从「一个类持有 19 个属性」变成
「一个结构体接收 19 个闭包」——**耦合总量没降，位置换了**。

数量对照：`spec/17` 删了 **16 个转发属性**，同期新增 **52 个闭包参数**（19+17+16）。
代码量 +15%（9,640 → 11,035 行），很大一部分就是这个。

**所以真正的问题是**：架构指标（文件行数、违规数、类型个数）全绿，
但「每个类型需要知道多少东西」这个更本质的指标从未被测量过。

## 目标与非目标

**目标**
- 为「耦合」定义**可测量**的指标，并量化 11 个对象各自的实际耦合度。
- 对每个对象给出处置结论：保留 / 减依赖 / 合并回去。
- 结论要能指导动手，不是泛泛而谈。

**非目标**
- 本轮**不改代码**（除非结论是「删掉某个纯增加间接层的类型」且改动极小）。
- 不动 UI 与业务逻辑。
- 不追求「依赖数降到某个数字以下」——先判断，不预设答案。

## 参考实现（Prior art）

- **《A Philosophy of Software Design》(John Ousterhout)**：把「模块的深度」定义为
  *功能价值 / 接口复杂度*。一个类型接口越宽（参数越多），即使实现再简单，也是浅模块。
  → **采用**：用「接口宽度」衡量，而不是「文件行数」。
- **Robert Martin 的 Stable Dependencies Principle / Afferent-Efferent Coupling**：
  用扇入（谁依赖我）与扇出（我依赖谁）衡量。
  → **采用**：为每个对象同时统计扇入与扇出。
- **Closure 注入的常见误用**：依赖注入的价值是**替换实现以便测试**。
  若注入的依赖从未被替换过（没有 mock、没有测试双），那注入只带来间接层。
  → **采用**：把「是否真的被测试利用」作为判据之一。
  → **不采用**：不引入 DI 容器或协议化所有依赖——那会引入更多样板代码，
  而本项目的真实问题是「依赖太多」而不是「依赖不可替换」。

## 方案

### 第 1 步：定义三个可测指标

| 指标 | 定义 | 怎么算 | 阈值参考（自定，非外部标准） |
| --- | --- | --- | --- |
| **扇出**（Fan-out） | 这个类型为了工作必须拿到多少个外部东西 | 数 `Providers` 字段 / `let` 依赖 | > 10 说明它其实是模型的一部分 |
| **扇入**（Fan-in） | 有多少地方用它 | `grep -c` 引用点 | 1 说明没有复用价值 |
| **测试利用** | 注入的依赖是否被测试替换过 | 搜测试文件是否构造过它的 Providers | 0 = 注入没换来可测性 |

**为什么用扇出而不是行数**：行数只反映「写了多少」，扇出反映「要知道多少」。
`LiveFrameApplier` 只有 200 行，但扇出 19——它对模型的了解程度不亚于原来的上帝类。

### 第 2 步：逐个对象量化

对 11 个对象（`ConnectionState` / `SessionStore` / `OutboxCoordinator` / `QuestionInbox` /
`JobRoster` / `Diagnostics` / `SessionAPI` / `SessionActions` / `NotificationBridge` /
`LiveFrameApplier` / `LiveStreamRunner`）统计三指标，形成表格。

**为什么必须逐个统计而不是抽样**：判据是「谁需要合并回去」，抽样会漏掉那个真正的罪魁。

### 第 3 步：按结论分三类处置

| 结论 | 判据 | 动作 |
| --- | --- | --- |
| **保留** | 扇出 ≤10 且扇入 ≥2 或确有独立职责 | 不动 |
| **减依赖** | 扇出 >10，但职责确实独立 | 把多个单项闭包聚成少数「能力」结构（如 `ConnectionCapability`），而不是 19 个散装闭包 |
| **合并回去** | 扇出 >10 **且** 扇入 = 1 **且** 测试利用 = 0 | 它没有独立价值，合并回 `ConnectionModel`，删掉 Providers |

**「合并回去」是承认拆过头**——这条必须写出来，否则自审只会为现有结构辩护。

### 第 4 步：把耦合纳入机器判据

在 `scripts/architecture-facts.sh` 里统计每个类型的 `Providers` 字段数，
超过阈值（暂定 12）即报告。**不一定要立刻当违规**，先作为观察项，
因为阈值本身还没被验证过。

### 第 5 步：更新架构文档

自审结论写进 `docs/architecture/OVERVIEW.md`（新建）：当前架构全景 + 各对象耦合度 +
关键决策索引。**之所以放在自审之后**：先写全景会把「52 个闭包」当成设计意图固化。

## 被否决的方案

| 方案 | 否决理由 | 否决依据 |
| --- | --- | --- |
| 直接继续加功能，等有问题再说 | 52 个闭包是「指标全绿但结构变差」的典型，不主动测就永远发现不了 | 本次盘点才发现 |
| 把所有注入改成「直接持有 `ConnectionModel` 弱引用」 | 那是回到上帝对象，且形成循环引用风险 | 原问题正是模型知道太多 |
| 引入协议化依赖（`protocol ConnectionProviding` 等） | 每个协议仍要 19 个方法，接口一样宽，只是从闭包换成协议；还多一层样板 | Ousterhout：接口宽度没变就是没变深 |
| 引入 DI 容器 | 为一个 App 引入容器属于过度工程 | 项目规模不需要 |
| **什么都不做** | 代价：每加一个功能，都要在 19 个闭包里挑几个传进去；新人读不懂哪些依赖是真需要的 | 本次盘点耗时本身就是征兆 |

**风险**（可能发生）

| --- | --- |
| 自审变成「为现有结构辩护」 | 预先写死「合并回去」的判据（扇出>10 且扇入=1 且测试利用=0） |

**为什么不该做这件事**（Drawbacks，诚实写反面）
- 当前指标全绿，功能可跑，真机验证通过。从「交付」角度看，现在就该去做用户要的功能，
  而不是回头审视架构。自审的收益是**未来**的维护成本，不是当下的功能价值。
- 如果接下来很长一段时间不加新功能，自审的收益就是零。

  注入的价值会重新成立——那时这条判据要重估。

## 自审结论

### 一句话结论

**我把「文件拆分」和「类型拆分」混为一谈了。** 文件该拆（控制行数），
但**无状态的流程不该独立成类型**，它们本就该是 `extension ConnectionModel`。

### 决定性证据

| 类型 | 扇出 | 扇入 | 测试利用 | **自有状态字段** |
| --- | --- | --- | --- | --- |
| `ConnectionState` | 5 | 2 | 否 | 4 |
| `SessionStore` | 5 | 5 | 否 | 多 |
| `OutboxCoordinator` | 2 | 1 | 否 | 2 |
| `QuestionInbox` | 5 | 2 | 否 | 有 |
| `JobRoster` | 1 | 2 | **是** | 有 |
| `Diagnostics` | 7 | 4 | 否 | 有 |
| `SessionAPI` | 2 | 2 | 否 | 有 |
| **`SessionActions`** | **13** | 2 | 否 | **0** |
| **`NotificationBridge`** | **17** | 2 | 否 | **0** |
| **`LiveFrameApplier`** | **19** | 3 | 否 | **0** |
| **`LiveStreamRunner`** | **17** | 2 | 否 | **0** |

**分界线是干净的**：扇出 >10 的四个类型，自有状态字段全是 **0**。

### 为什么这是错的

一个类型「自有状态为 0」且「要注入 17 个闭包才能工作」，含义是：
**它不是独立单元，它是那个类的流程片段**。给它注入 17 个闭包，
等于用依赖注入模拟「我是 `ConnectionModel` 的一部分」——纯增加间接层。

三个指标同时指向同一个结论：
- 扇出 17–19（需要知道模型里的几乎每件事）
- 测试利用 0（注入没换来可测性，因为 App 层没有测试 target）
- 自有状态 0（没有自己的数据要保护）

### 正确的终态

```swift
// ✅ 文件拆开，类型不拆（无状态的流程用 extension）
ConnectionModel+Live.swift     extension ConnectionModel { follow / acceptLive ... }
ConnectionModel+Notify.swift   extension ConnectionModel { syncPush / sendReply ... }  ← 合并回来
ConnectionModel+Send.swift     extension ConnectionModel { performSend ... }
ConnectionModel+History.swift  extension ConnectionModel { loadHistory ... }

// ✅ 有状态的才是独立类型（被视图直读）
ConnectionState / SessionStore / OutboxCoordinator / QuestionInbox / JobRoster / Diagnostics
```

**判据（新）**：
- **有自有状态** → 独立类型（状态对象），被视图/其他对象读取
- **无自有状态** → `extension`，直接用宿主的状态
- **文件行数超阈值** → 拆文件，不拆类型

### 与 spec/13 的关系

`spec/13` 的「5 个状态对象」目标**没有错**——它说的对象（`Diagnostics` / `JobRoster` /
`ConnectionState` / `OutboxCoordinator` / `SessionStore`）全部有自有状态，拆得对。

错的是我在 `spec/17` 之后又额外抽了 4 个**无状态流程**类型，那是为凑文件行数产生的。
所以本结论**不否定 spec/13**，只否定后来的过度抽取。

### 机器判据已加入

`stateless-type-smell`：`/Session/` 下自有状态为 0 且注入依赖 >8 的类型即违规。
当前报出 4 处（即上述四个类型），**这是要还的债，不是新债**。
