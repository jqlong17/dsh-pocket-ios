# 归档：2026-11-12 之前写的 spec

这 18 份 spec 保留原样，**不补写、不回改**，只作为历史记录。

## 为什么归档

不是内容错了，而是**格式不规范**。2026-11-12 引入 [`../00-TEMPLATE.md`](../00-TEMPLATE.md) 后，
这批文档的缺段会持续误导后来的执行者（AI 或人）：照着缺段的样板写，就会继续缺。

**归档而不是补写的理由**：spec 的价值在执行期。这些文档对应的代码已经迭代数轮，
现在补写「当初为什么这样做」，写出来的是编造出来的决策过程，比空白更糟。

## 不规范点清单（未来 AI 请勿再犯）

### 1. 数字编号（最该改的一条）

`01`…`18` 这种从 1 开始的连号，**插入一份就必须重排后续所有编号**，
而重排意味着改文件名、改引用、改检查点记录里的 `spec` 字段。实际结果是：宁愿把内容硬塞进现有编号，也不新增一份。

**改为日期时间编号**：`spec/2026-11-12-2350-slug.md`。天然有序、可无限插入、能看出时间线。

### 2. 缺 Status

18 份里靠人肉看正文的 ✅ 才知道哪些还活着。**这是最先暴露的问题**——问「还剩什么没做完」时，
只能一份份翻。

**必须**：开头写 `> Status: Draft | In Review | Accepted | Superseded`。

### 3. 缺「被否决的方案」（14/18 份）

只有 17 号写了。后果是实测出来的：删转发层时我用全局正则替换，
把「定义者」（状态对象本身）也改坏了，连续 8 轮编译失败——**如果当初凭证/重构类 spec 里
写死了「只改使用者侧，不改定义者侧」这条被否决方案，就不会重犯**。

**必须**：单独成段，含「什么都不做」的代价。

### 4. 缺「未决问题」（18/18 份全缺）

「App 层没有测试 target，所以做不了真正的 TDD」这类结构性缺口，
当时只在对话里说过，没落到文档。下次接手要重新发现一遍。

### 5. 只有「风险」没有「代价」

`spec/13` 的「代码量 +15%」是我事后补的。**代价是确定发生的**（一定会付），
风险是可能发生的——两者混在一起写，读者会以为 +15% 只是「可能」。

### 6. 测试计划不标 target（01–10 全缺，11 之后才有）

写不出 target 就说明它不可测。01–10 写的「跑端到端测试」这种没法执行——
哪个 target？什么命令？后来才知道要具体到 `DSHKitTests.XxxTests`。

### 7. 预估工时凭直觉

`spec/13` 估 5–7 小时，实际约 2 小时。49 个检查点样本显示倍率稳定在 **0.61×**，
说明是估算模型错误，不是偶发。**必须按单元累加**（见模板「预估工时」段）。

### 8. 早期 01–10 只有 2–3 段

它们本意是「模块清单」而不是 spec，却被放进了 spec 目录、按 spec 编号，
导致「spec 目录里大部分文件不符合 spec 标准」。
