## 背景 / 问题

**有证据**：用户真机实测日志

```
14:46:14  用户点击发送
14:46:32  才写入断网暂存       ← 中间 18 秒，界面一直显示「发送中」
14:46:59  网络恢复
14:47:00  补发完成
```

**根因**（不是猜的，是读代码确认的）：`performSend` 没有网络预判，走「先试 → 失败 → 分型」：
重试 3 次（退避 800/2000/3000ms），每次还可能等 TCP 超时 20 秒，三次失败才判 `holdOffline`。

**反差点**：`NWPathMonitor` 当时就知道不可达——它就是 27 秒后触发补发的那个监听，
只是状态没暴露给发送路径。

## 目标与非目标

**目标**
- 网络明确不可达时，点发送立即进入断网暂存（不等重试）。
- 可达或状态未知时，行为与现在完全一致。

**非目标**（写出「这次不动什么」，防止顺手扩张）
- 不处理「假连接」（有 Wi-Fi 信号但网关不通）——那类仍靠超时兜底。
- 不改重试次数与退避节奏。
- 不替代 `SendFailurePolicy` 的失败分型，预判只是提前走同一条路。

## 参考实现（Prior art）

- **Alamofire 的 `NetworkReachabilityManager`**：只用可达性做快速失败，不做成功保证。
  → **采用**这个定位：可达 ≠ 能连上，所以预判只用于「省掉等待」，不用来「保证成功」。
- **不动点**：不引入 ping / HEAD 探测。**不采用**的理由：会引入新的延迟与失败点，
  而我们只想解决「已知不可达还硬等」这一种情况。

## 方案

### 第 1 步：DSHKit 加纯策略

- 做什么：`SendPreflightPolicy.action(isReachable: Bool?) -> .send / .holdOffline`
- **为什么这么做**：判定是纯函数，边界（nil/true/false）可穷举测试；App 层没有测试 target，放进去就测不到。
- **为什么不那样做**：不把判断写在 `performSend` 里——那样三个边界只能靠真机试，回归时无从覆盖。
- 改动范围：`DSHKit/Sources/DSHKit/Protocol/SendPreflightPolicy.swift`（新）

### 第 2 步：`NetworkWatcher` 暴露 `isReachable`

- 做什么：`private(set) var isReachable: Bool?`，`nil` 表示尚未探测。
- **为什么用 `Bool?` 而不是 `Bool`**：`NWPathMonitor` 首次回调前没有状态。若把 nil 当成不可达，
  App 冷启动头几秒发的消息会被错误暂存——用户会看到「现在断网」但网络是好的。
  **「不知道」必须等同于「可以试」**，这是本方案最容易写错的边界。
- 改动范围：`DSHPocket/Session/NetworkWatcher.swift`

### 第 3 步：`performSend` 接入

- 做什么：在**写完发件箱之后**、发请求之前插入预判。
- **为什么是这个位置**：必须在写入发件箱之后，否则预判后 `return` 会丢掉用户输入。
  顺序是「先保命，再优化」。
- **为什么不另写一套状态写入**：复用 `holdOffline` 的同一组写入（`queuedSendRpcIds` +
  `markOutboxHeldOffline`），否则补发候选集会漏掉预判写入的条目。

## 被否决的方案

| 方案 | 否决理由 | 否决依据 |
| --- | --- | --- |
| 全局正则批量替换调用点 | 无法区分「定义者」与「使用者」，会改坏状态对象本身 | 实测：8 轮编译失败 |
| 在 `performSend` 里内联判断（不上沉 DSHKit） | nil / true / false 三个边界无法单测 | App 层没有测试 target |
| 引入 ping 探测确认「真的不可达」 | 增加新延迟与失败点，且我们的目标只是省掉已知的等待 | Alamofire 也只做快速失败 |
| **什么都不做** | 代价：断网点发送要等 2.8–62 秒，用户以为卡死 | 用户实测 18 秒 |

## 代价与风险

**代价**（确定会付）
- 多一个策略类型（约 30 行）+ 3 条测试。
- `NetworkWatcher` 多暴露一个状态，调用方需理解 `nil` 的语义。

**风险**（可能发生）
| 风险 | 缓解 |
| --- | --- |
| nil 被当成不可达 → 冷启动消息被误暂存 | 策略明确 nil → `.send`，单测锁定 |
| 误判可达（假连接）→ 仍要等超时 | 不改变兜底路径，最坏情况与现状相同 |

**为什么不该做这件事**（Drawbacks，诚实写反面）
- iOS 的可达性判断本身不可靠：Tailscale 刚起来、Wi-Fi 已连但 DNS 未就绪时都可能误报「可达」。
  这时候预判反而让人以为「网络是好的」，而实际发不出去——多一层判断就多一层解释成本。

## 未决问题（Unresolved Questions）

- 是否应该在多次发送失败后**主动降级** `isReachable`（把应用层观测到的失败反馈给监听器）？
  这能覆盖「假连接」，但会让状态机更复杂，本次不做。
- 断网时的 UI 文案「现在断网，等联网时将一并发送」在「其实可达但请求失败」时会误导吗？
  需要一次文案走查。
